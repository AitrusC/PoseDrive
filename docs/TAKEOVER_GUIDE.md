## 1. 项目目标与当前阶段

**PoseDrive 是 Maya 骨骼姿态修型驱动的创建与管理工具。当前已形成可运行、可测试的 UI 原型，左侧集合交互已经打通；真正的姿态驱动和修型输出尚未实现。**

用户已确认：“Pose”指骨骼当前姿态。例如 `hand_R` 的 Y 轴旋转为 `60°`，可以记录为一条 Pose；这里不是指角色资产或预设配置。

目标链路：

```text
选择已有骨骼 hand_R
    → 加入骨骼集合
    → 记录中性姿态与目标 Pose（例如 Y = 60°）
    → 创建并计算该 Pose 的驱动值
    ├─ 驱动已有 BlendShape 的某个目标权重
    └─ 通过驱动关键帧控制修型骨骼的指定属性
```

最终应当做到：用户关闭 PoseDrive 窗口后，旋转骨骼仍能驱动修型；保存并重新打开 Maya 场景后，驱动网络与工具记录仍可恢复。

当前不能用“UI 看起来完成了多少”推算整个工具的完成比例。更准确的阶段判断是：**已完成第一阶段的一部分（UI 原型），即将进入姿态定义与第一个真实驱动闭环。**

### 1.1 四个概念要分开

| 概念 | 含义 | 示例 |
|---|---|---|
| 驱动骨骼 | 提供姿态输入的已有场景骨骼 | `hand_R` |
| Pose | 一次姿态采样及其识别规则 | Y 轴目标角度 `60°`、基准角度、响应范围 |
| Pose 输出 | 随骨骼变化而计算的标量驱动值 | 设计上的 `0…1` 激活值 |
| 修型目标 | 接收驱动值的输出对象或属性 | `blendShape1.weight[3]`，或修型骨骼 `translateY` |

“添加骨骼集合”是把已有骨骼纳入工具管理，不等于创建一根 Maya 骨骼。“添加 Pose”是采样并建立驱动记录，不等于自动雕刻出一个修型模型。

## 4. 继续开发前，要先定义 Pose 的语义

用户给出的 `hand_R`、Y 轴 `60°` 示例足以选择一个较小的第一版范围，但还需要区分两种不同功能。

### 4.1 单轴响应与完整姿态识别

| 模式 | 含义 | 适合的第一步 |
|---|---|---|
| 单轴驱动 | 只读取选定轴；X/Z 改变时，Y 相同仍产生相同值 | 推荐作为第一条可验证链路 |
| 完整姿态识别 | 判断骨骼的整体朝向或多个输入与采样姿态的接近程度 | 后续评估姿态插值或多维 reader |

例如，`(X=0,Y=60,Z=0)` 和 `(X=45,Y=60,Z=30)` 在单轴模式下完全相同，在完整姿态识别中可以是不同 Pose。UI 必须标明模式，不能把单轴映射宣称为通用姿态识别。

### 4.2 首版建议：显式基准 + 单轴范围

先支持普通、可直接读取旋转通道的骨骼，用户明确选择输入属性、记录基准和目标：

```text
输入：hand_R.rotateY
基准：0°（示例值；由用户采样，不假定所有骨骼基准都是 0）
目标：60°
响应：从基准到目标单调增加，超过目标维持最大激活
输出：0…1
```

可用于原型验证的数学定义：

```text
w = clamp((当前角度 - 基准角度) / (目标角度 - 基准角度), 0, 1)
```

这是建议实现的单轴映射，不是现有代码。它也不是以 60° 为中心的峰值识别器。

| Y 角度 | 示例预期输出 |
|---:|---:|
| -30° | 0 |
| 0° | 0 |
| 30° | 0.5 |
| 60° | 1 |
| 90° | 1 |

如果希望超过 60° 后权重重新下降，就需要定义进入、峰值、退出范围及衰减曲线，不能继续使用这个单调映射。基准和目标相同应拒绝创建，避免除零。

### 4.3 多轴、旋转空间和求解器的后续边界

首版要把支持范围写进 UI 和测试。不能仅凭三个 Euler 通道数值，承诺处理旋转绕回、不同旋转顺序、`jointOrient`、父级变换、约束或 `offsetParentMatrix` 驱动的所有角色。

需要完整姿态识别时，先比较两条路线：

| 路线 | 收益 | 成本／验证点 |
|---|---|---|
| Maya Pose Interpolator | 复用 Maya 已有姿态插值能力 | 目标版本 API、Pose 类型、neutral、插值影响、输出范围、编辑与删除语义 |
| 自建矩阵／四元数姿态 reader | 可精确定义项目所需的空间和响应规则 | 朝向差异、swing/twist、跨界连续性、归一化、求值和回归测试均需自行负责 |

Autodesk 的 Pose Editor 本身就是读取骨骼变换、通过姿态插值驱动 BlendShape 权重的系统，因此它值得作为多轴路线的技术验证对象；不需要一开始就自行实现完整求解器。[官方 Pose Editor 说明](https://help.autodesk.com/cloudhelp/2022/ENU/Maya-CharacterAnimation/files/GUID-2AB6C4C3-75AC-4094-A65C-C232739AFB30.htm)

后端选择应由一个最小场景验证决定。本轮没有创建 Pose Interpolator，也没有确认其全部 API 在本机的实际行为。不要将不同后端的输出默认视为相同，也不要假定所有插值模式天然满足严格 `0…1`。

驱动骨骼若由控制器驱动，采样与回到姿态应通过合适的控制器输入实现。工具需要分别记录“读哪个骨骼”和“如何恢复控制器姿态”；只存骨骼旋转并不足以还原 IK 角色的姿态。

## 5. 建议保留和重构的范围

**保留 UI，实现一个小而清晰的业务核心；不建议全面重写，也不建议继续把业务塞进控件。**

### 5.1 可以保留

- 无边框窗口、图标、主题、滚动与动画实现。
- 集合按 ID 复用的方式，以及选择／展开相互独立的约定。
- `test_ui.py` 的手动测试方式，继续作为不依赖 Maya 场景的开发入口。
- 26 项 UI 测试，作为接入业务时不能破坏的基线。

### 5.2 需要逐步调整

| 部位 | 调整方向 |
|---|---|
| `BodyWidget` | 接收操作服务和展示数据；不直接查 Maya 节点、创建网络或依赖容器内部字典 |
| `JointPosePreviewData` | 保留为预览实现；真实场景数据走另一个实现，不把它扩充成万能业务对象 |
| `PoseEditWidget` | 真正读取选中 Pose，增加采样信息、实时输出和目标绑定编辑 |
| `interface/gui.py` | 从产品链路退役；其两个全局列表不适合作为正式数据源 |
| `interface/protocol.py` | 随第一条业务链路明确接口，分开数据、场景操作与视图职责 |
| 正式启动入口 | 从 `test_ui.py` 分离；保留原公开启动函数，测试入口仍独立可用 |

协议层的具体遗留项：`abstractmethod` 缺少 ABC/ABCMeta 支持；`create`/`load` 约定不统一；类型注册无重复校验；`view()` 让协议依赖 Qt；`destroy()` 没有区分工具记录和场景对象。不要先把所有旧方法补满再做功能，只落实首个用例确实需要的接口。

### 5.3 逐步形成的分层

```text
UI：选择、展示、发出用户操作
    ↓
应用服务：添加集合、采样 Pose、创建驱动、绑定目标、删除、恢复
    ↓
数据模型：集合、Pose、输出绑定、稳定 ID、版本
    ↓
Maya 适配层：选择查询、节点引用、属性读写、DG 网络、SDK、场景存储
```

预览和真实模式复用 UI，但由不同的数据／服务实现提供内容。可以先从两个或三个小模块开始，不必一次性创建完整框架、事件总线或插件系统。

建议未来按功能逐步增加：`core/models.py`、`services/pose_service.py`、`maya_adapter/scene.py`、`maya_adapter/drivers.py`、`maya_adapter/targets.py`、`maya_adapter/storage.py`。这些路径只是方案，当前不存在。

## 6. 正式数据至少需要表达什么

| 记录 | 建议字段 | 解决的问题 |
|---|---|---|
| 工程／场景记录 | schema_version、工具版本、集合列表 | 场景重开、格式迁移 |
| 骨骼集合 | collection_id、显示名称、driver_node_ref、poses | 集合归属、场景绑定 |
| Pose | pose_id、collection_id、名称、输入模式、基准、目标采样、响应参数、启用状态 | 准确定义这一条姿态 |
| 驱动网络记录 | 后端类型、节点引用、输出 plug、工具拥有的节点 | 查询、重建、删除 |
| 输出绑定 | binding_id、pose_id、类型、目标节点／属性、映射参数 | 一个 Pose 同时驱动多个修型目标 |
| UI 状态 | 当前选择、展开集合、过滤文字 | 不与驱动业务数据混在一起 |

节点显示名称和 DAG 路径都可能变化。建议在场景内用明确的节点连接表达关联，辅以持久化标识和诊断信息；引用、多角色实例、节点删除重建需要单独设计解析规则，不能只保存短名或只假定 UUID 足够。

第一版可用工具拥有的 metadata/network 节点保存版本、Pose 参数和节点关联，跟随 `.ma/.mb` 保存。JSON 可用于导入导出，但只放 Python 内存或外部 JSON 不会自动建立可恢复的场景关联。

## 7. 两种修型输出应怎样接入

### 7.1 BlendShape 输出：先连接已有目标

首版只做：选中已有 BlendShape 的某个目标权重，将 Pose 输出映射到它。目标几何的雕刻、反求、镜像可以后置。

```text
姿态输入 → Pose 驱动输出 → 可选的强度／重映射 → blendShape.weight[index]
```

必须区分 BlendShape 节点、目标索引和展示别名；UI 展示别名，绑定不能只靠名称文字推断。

创建前检查目标是否存在、是否可写、是否已有输入。首版遇到已有输入应明确报告冲突；不使用强制连接把原驱动断掉。绑定失败不能留下半套网络。

本阶段不自动改变 skinCluster / blendShape 顺序或修型空间。后续若加入“从当前变形模型创建修型”，需要独立确定 pre/post deformation、变形空间和目标生成流程，不能当成连接权重的附属步骤。

### 7.2 修型骨骼输出：通过驱动关键帧映射属性

先支持一个已存在、没有冲突输入的修型骨骼属性：

```text
Pose 输出 → animCurve → corrective_joint.translateY
```

例如：Pose 输出为 0 时，修型骨骼 `translateY = 0`；输出为 1 时，`translateY = 2`。若原始静止值是 5，就应记录 5 作为基准，而不是强制设为 0。

Maya 的驱动关键帧以驱动属性而非时间作为曲线输入；`setDrivenKeyframe` 支持指定 `currentDriver`、`driverValue` 和目标 `value`。这与“在时间轴上打两帧”不同。[官方命令文档](https://help.autodesk.com/cloudhelp/2022/ENU/Maya-Tech-Docs/CommandsPython/setDrivenKeyframe.html)

首版明确切线和超出区间行为，不依赖用户全局默认值。多个 Pose 驱动同一目标属性时必须另外定义组合策略；不要默认多个绝对值简单相加，否则会重复叠加静止偏移。第一版可以拒绝此类冲突，后续再做基准加增量等明确组合。

禁止通过“移动修型骨骼再读取驱动骨骼”制造求值环；驱动源和输出目标的依赖关系需要检查。

### 7.3 UI 关闭后驱动仍须运行

正式驱动应由 Maya DG 节点或经过验证的求解器计算。Qt 定时器、界面滑块和 `scriptJob` 可用于刷新显示，不应成为每帧计算修型权重的唯一来源。

实时预览若需要临时覆盖驱动值，应有显式覆盖模式并能恢复正常求值；不能直接对一个已经被连接的输出属性反复 `setAttr`。

## 8. 接下来如何开发：按可验收成果推进

### 阶段 A：建立接手基线

工作：

- 保存当前工作区变更，人工审阅后建立版本基线；本次没有替用户提交或覆盖改动。
- 确定日常使用的目标 Maya 版本。当前可复现环境为 Maya 2022，不代表用户必须使用该版本。
- 运行 26 项测试，手动启动 UI，读完第 3 节的核心文件。
- 明确首版是单轴模式，并确定超出目标后的响应规则。

验收：能解释添加一次集合和添加一次 Pose 分别走哪条调用链，知道测试数据在哪改。

### 阶段 B：补齐 Pose 编辑 UI，继续用手动数据

工作：

- 在测试数据中加入输入轴、基准角度、目标角度、模拟输出和绑定目标记录。
- 右侧显示当前 Pose 名称、所属骨骼、输入模式、基准／目标值、启用状态。
- 底部“SHAPE 列表”改为能容纳两种输出类型的“修型目标”列表。
- 先实现目标表单的新增／编辑／删除与选择同步；二维姿态画布放后面。
- 读数与编辑分开：改变表单不应无意覆盖已记录的 Pose。

验收：在 `test_ui.py` 配置 `hand_R_Y60`，切换不同 Pose 时右侧内容正确且互不覆盖。

### 阶段 C：第一次接 Maya，只绑定和读取

工作：

- 顶部加号读取 Maya 所选 joint，绑定已有节点；定义空选、多选、重复添加规则。
- 记录中性姿态，再把当前轴值采样成 Pose。
- 同名不同节点必须区分；改名更新展示，删除节点标记失效。
- 建立最小场景 metadata，保存后重开恢复集合与采样信息。

验收：真实 `hand_R.rotateY=60` 可被记录，UI 数据来自场景；此时还不必生成修型输出。

### 阶段 D：做出第一条真实闭环，优先 BlendShape

工作：

- 在隔离测试场景实现单轴范围驱动，暴露可查询输出属性。
- 添加一个已有 BlendShape 目标绑定。
- 支持删除该绑定、撤销和重做；连接冲突与失败要能清理。
- 保存、重开、关闭工具后继续检查求值。

验收示例：`hand_R` 的 Y 从 0 → 30 → 60 时，驱动值和目标权重为 0 → 0.5 → 1（按第 4 节定义）；窗口关闭后结果相同。非零基准、负方向也有测试。

### 阶段 E：增加 SDK 修型骨骼输出

工作：

- 复用同一个 Pose 输出，增加目标骨骼及属性选择。
- 记录目标属性的基准值和修型值，建立驱动曲线。
- 检查既有动画／约束／连接冲突，暂不自动混合复杂网络。
- 删除工具创建的绑定时，仅清理工具拥有的节点与连接。

验收：同一 Pose 可分别驱动一个 BlendShape 和一个修型骨骼；删除其中一个绑定不影响另一个；Undo/Redo 恢复正确。

### 阶段 F：扩展为可用于角色的姿态系统

在前面闭环稳定后，再加入多轴识别、控制器驱动骨骼、镜像、批量、多 Pose 组合、引用资产、二维编辑器、导入导出和性能优化。

验收以真实角色的完整活动范围为准，包含中间姿态、组合姿态、极限姿态，既检查数值也检查修型观感。

## 9. 测试与第一版完成标准

现有 UI 测试继续保留，新增测试分成三层：

| 层级 | 环境 | 内容 |
|---|---|---|
| 数据／算法 | 不依赖 Maya 和 Qt | 基准／目标、负方向、边界、ID、序列化、归属 |
| UI | 当前 mayapy + Qt | 切换编辑、不串数据、增删绑定、无有效选择时禁用操作 |
| Maya 集成 | 独立测试场景或 Maya standalone | 节点、连接、数值、Undo/Redo、保存恢复、冲突清理 |

Maya 集成测试从零创建测试场景，不在未保存的生产场景中清空或替换数据。自动测试证明网络与数据正确；真实 Maya 交互和变形检查仍需补充。

第一版发布前至少满足：

- [ ] 一个真实骨骼可以被加入，重复点击不创建重复集合。
- [ ] 能记录基准和一个单轴目标 Pose，输入模式清楚可见。
- [ ] 示例角度输出符合预先定义；比较使用明确容差，例如标量误差 `1e-5`（建议测试门槛）。
- [ ] 一个 Pose 可以绑定一个已有 BlendShape 目标。
- [ ] 一个 Pose 可以通过 SDK 驱动一个无冲突的修型骨骼属性。
- [ ] 关闭工具后求值不变，保存／重开场景后恢复同一网络和记录。
- [ ] 改名不串对象，节点丢失时可诊断，删除集合不会误删用户驱动骨骼或已有目标。
- [ ] 创建、删除、采样更新可以撤销／重做，UI 能跟随恢复。
- [ ] 创建到一半失败不会留下孤立节点或错误 metadata；Undo chunk 本身不等于自动回滚。
- [ ] 已存在的目标连接不会被静默覆盖，重复执行不会累积重复网络。
- [ ] 用测试角色检查完整活动范围，发现不支持的姿态或绑定结构时明确报告。

## 10. Maya 版本与兼容策略

当前代码直接导入 PySide2、使用 shiboken2。Maya 2025 已迁移到 Qt6 / PySide6，不能仅凭 Maya 2022 测试通过就宣称支持新版本。[Autodesk Maya 2025 API 更新说明](https://blog.autodesk.io/maya-2025-api-update-guide/)

建议先确定一个主版本，再视需求增加 Qt 兼容入口统一导入。若同时支持 Maya 2022 和 2025+，除导入外，还要验证事件位置接口、枚举、宿主包装、窗口标志和实际交互；不要只做一次 try/except 就结束兼容工作。

开发中使用的 Python 语法和依赖也应服从目标 mayapy 版本。系统 Python 3.14 不能替代 Maya 2022 的运行验证。

其余事项可按阶段决定，不必阻塞当前 UI 迭代：

| 决策 | 本文建议 | 最迟决定时间 |

| 首版姿态识别范围 | 单轴，明确输入属性与基准 | 驱动实现前 |

| 多选骨骼添加 | 建议逐个建立集合并显示处理结果 | 选择接入前 |
| 修型模型的自动生成 | 第一版只连接已有目标，不自动雕刻或反求 | BlendShape 接入前 |
| IK/FK、OPM、参考资产 | 明确为后续扩展，不暗示首版全部支持 | 扩大测试角色范围前 |
| 发布能力 | 明确是 Maya 内工具；游戏引擎导出另行评估 | 有导出需求时 |
